# Changelog

What changed in each release, for people who run rendimiento. Every change is in the [merged pull requests](https://github.com/rendimiento-ai/rendimiento/pulls?q=is%3Apr+is%3Amerged); a release's notes on GitHub list them all.

What is not released yet is in `cambios/`, one file per change; each release gathers them here.

## Unreleased

## v0.3.0 (2026-11-25)

- **Two API replicas:** after the setup page makes the GitHub App, every API replica loads it, not only the one that served the setup; before, a request served by the other one could answer that GitHub was not configured until it restarted.
- **Releases:** when a release fails verification, what its pods showed is kept before the rollback removes them: each service's new ReplicaSet and pods with their containers' state, restarts and last exit code, the last 200 lines of each container's log (and of the run before its last restart), and the last 50 events about them; on a computer, its containers' state, exit code and last lines. Lines that look like secrets are left out, at most 64 KiB a release, kept 30 days. It shows under the release in Releases ("What was seen when it failed"), on its entry in Problems, and to agents in `app_estado` and the coding agent's `app_status`.
- **Deploy:** the platform's ClusterRole may now `get` and `list` events (`deploy/rbac.yaml`, the chart too): run `make deploy` once, or it keeps the rest of the evidence and says it could not read the events.
- **Encargos:** an encargo the coding agent gave back has an optional note, **What it should know when it tries again**, on its card in «The agent» and in Encargos; **Send it again** and **Leave it to my agent** carry it (`notes` by id on `POST /api/encargos/do`, `note` on `POST /api/encargos/{id}/route`; older clients without them still work). It is kept in the encargo's history as `told`.
- **Coding agent:** an encargo given back before starts with why it stopped last time and what the person answered when sending it again; `encargo_leer` and `encargo_tomar` show both (`solto`, `la_persona_dijo`).
- **Coding agent:** each app's sandboxes keep their tools' caches (Go's modules and build cache, npm's, pnpm's, yarn's, pip's) in a volume of their own, `sandbox-cache-<app>` in `rendimiento-builds` (10 GiB, `CODER_SANDBOX_CACHE_SIZE`, on `TEST_CACHE_STORAGE_CLASS`), so an encargo no longer starts cold. A new one is seeded once from the matching CI cache, mounted read-only; nothing goes from a sandbox to CI, and no CI step mounts it. The janitor removes it after 14 days unused, and deleting the app removes it.
- **Coding agent:** a folder whose test or task has `postgres: true` gets the steps' throwaway Postgres beside its sandbox, with `DATABASE_URL` and `TEST_DATABASE_URL` (`synchronous_commit=off`), so database tests run there instead of skipping.
- **Coding agent:** `CODER_SANDBOX_TIMEOUT` sets the most one command runs (15m); one that runs out of time answers what it printed so far and how long making the sandbox took, and the agent is told to prefer narrow commands. The sandbox's CPU limit is now 3 (`CODER_SANDBOX_CPU`), its request still 250m.
- **Security:** the platform-update endpoint now reads at most 1 KiB of its request body, as the other endpoints do.
- **Coding agent:** the `run` tool's sandbox clones a private repository again: it gets the app's installation token, as a run's steps do, instead of cloning anonymously ("could not read Username for 'https://github.com'"). It clones from the app's forja (GitLab and Bitbucket apps no longer clone from github.com), and before the agent's first commit it starts from the commit its branch started from.
- **Fixes:** declared fixes (the coding agent's `run_fix`, the run page's button and Renovate's branches) clone with the app's installation token and from its forja too, so they work on private repositories and on GitLab and Bitbucket apps.
- **Caminos:** an app with `previews:` starts its Roads tab with **Live copies · N of max**: a card per copy (its pull request, address, branch, commit and run, health, its own tests and its checks en seco, memory, the day it goes; a short copy en seco dashed), the memory they hold (in use, from the metrics server, or asked for), the cluster's share of all apps' copies against the 10% cap, the copies deleted in the last 7 days and why, and the Secrets a copy does not have (names only).
- **Caminos:** a person who may merge can make a copy again with its branch's last commit that passed, keep it 3 more days (up to 30 after its last push) or delete it now, from its «⋯» menu; each is in the bitácora, its pull request's comment says so, and a copy a person deleted comes back only with the next push. An agent's key cannot.
- **Caminos:** each branch with a live copy has a **live copy** badge, and a little house with its number at the end of its road on the map (a button: keyboard and screen readers reach it); the glance has **N live copies**, linking to the section.
- **Database:** a new table, `copias` (only added): each copy's run, its own tests' result, a person's extension, and when and why it went.
- **Deploy:** `deploy/rbac.yaml` and the chart let the platform read pod metrics (`metrics.k8s.io` pods), for the memory copies use; without `make deploy` the tab shows what they ask for instead.
- **Previews:** a copy (a pull request's, or a short one for checks en seco) now gets each secret `X` its app reads from the app's preview variant `X-preview`, copied into the copy's namespace as `X` with the same type and keys. Production's `X` is never copied: without `X-preview` the copy runs without `X`. The controller keeps them in sync on every reconcile of the copy and at once when an `X-preview` is saved or deleted, and the copy's pods roll when they change. On a computer, copies' containers read `X-preview` too, taking an edit at their next refresh.
- **Previews:** on an app's Settings page, each secret shows its **Preview** variant (whether it exists, its keys, never values), set the same way by administrators; saving it does not restart the app. `GET /api/apps/{app}/preview-secrets` lists, by name, the secrets the app's copies run without.
- **Secrets:** the app's own tests' `secretEnv` (`tests:`) now counts among the app's secrets, so it can be set on the Settings page.
- **Previews:** rendimiento's own app (`rendimiento-ai`) turns on `previews:` (`keep: 3`, `max: 2`): a pull request opened from this repository gets a copy of the book at `learn-pr-<number>.rendimiento.ai`. Only `docs` is a service of this app; the platform is a build and is never deployed by it, so a copy never starts a second platform.
- **Encargos:** the «⋯» menu of an encargo stays on the screen on a phone; it no longer opens off its left edge when the button wraps to its own row.
- **Coding agent:** it can ask you (`ask`) instead of giving an encargo up when it needs your word: it commits what it has, stops without spending, and the question shows first on Ruta → For you and in the bell. **Answer and let it go on** resumes it on the same branch with your answer; **Pass it to my agent** gives it to your own agent with the question, and so does a question nobody answers in 3 days. Only a person signed in can answer (`POST /api/encargos/{id}/answer`, `/pass`).
- **Coding agent:** read-only tools for the encargo's own app only: `runs` (step durations and status, by branch or step), `step_log`, `slow_requests` (the Log page's slow requests and the traces' slow ones) and `app_status` (releases, open problems, the lookout's findings). An encargo from the lookout is told to verify its numbers with them first.
- **Coding agent:** it no longer gives up for what passes by itself: a dropped connection or a busy AI API is tried again up to 3 more times, a forja's 5xx once more, a run longer than 50 minutes is waited for (up to 6 hours, spending nothing), and a run the cluster failed (etcd, an evicted pod, an image pull) runs once more with the platform's retry.
- **Database:** migration `0065_encargo_preguntas.sql` adds the encargo status `asking` (widening the status check) and the table `encargo_preguntas` (only adds: the previous version never writes nor reads them).
- **Coding agent:** a `run` tool runs any shell command (installs, tests, linters, git) in a sandbox pod with the repository at its branch and its uncommitted changes; the files a command changes become its changes, and it is told to run the tests touching its change before `commit_and_test`. Each command shows in the encargo's history; it costs no AI money, only time.
- **Coding agent:** the sandbox runs in the build namespace on worker nodes only, with no service account token, no secrets or platform environment, not root, all capabilities dropped, seccomp `RuntimeDefault`, a sized `emptyDir` workspace, 2 CPU / 4Gi, 15 minutes a command; it is kept for the encargo and removed when it ends, after 30 idle minutes, or by a janitor.
- **Coding agent:** a new NetworkPolicy, `isolate-sandbox`, lets sandboxes reach DNS and the public internet only (not the cluster, the nodes, the home network or BuildKit), and `isolate-builds` now leaves them out. The platform also makes it before any sandbox starts.
- **Coding agent:** on the AI page, **Run commands in a sandbox** turns the tool off for an organization (on by default). `CODER_SANDBOX=off` turns it off for the platform; `CODER_SANDBOX_IMAGE`, `CODER_SANDBOX_RUNTIME_CLASS` (empty: the cluster's default runtime; for gVisor or Kata later), `CODER_SANDBOX_CPU`, `CODER_SANDBOX_MEMORY` and `CODER_SANDBOX_DISK` tune it.
- **Deploy:** `deploy/` changed (the builds Role may now exec into pods, and the new NetworkPolicy): run `make deploy` once, or the tool answers that exec is not allowed.
- **AI page:** «How the coding agent is doing», beside the coding agent's settings: over the last 30 days (or 7, 90, or all of it), what it finished at the first try or after another, what it gave back to your own agent and why (cause by cause, with the encargos), what you accepted the first time or sent back, what it spent against the estimate by difficulty, the factor the estimator applies today, and a warning when it gave back three in a row for the same cause. Every member who sees the AI page reads it (`GET /api/ia/cuentas`).
- **Coding agent:** it records why it gives an encargo back (its brake, a person's stop, a restart, an error, or the cause the model gives with `give_up`), in a new nullable column of the encargos' history; older releases are classified by their note, approximately.
- **Computer:** rendimiento on a computer can sleep from the top bar's **Sleep** button (administrators only; hidden in a cluster): the apps' containers and the CI stop, data, releases and the Ruta stay, and the state is kept so a restart stays asleep. A publish going on is waited for, or cut with «Without waiting» (the app stays on its release; the new one publishes on waking).
- **Computer:** runs cut by sleep go back to the queue and run again on waking, never marked failed; the forjas' webhooks received while asleep are kept and handled in order on waking; apps answer «Back soon» (503) through the proxy; the lookout leaves out the hours asleep.
- **Computer:** **Wake up now**, or a daily hour to wake at (off by default), starts the same containers and shows a summary of what it did; **Shut down completely** sleeps and then stops rendimiento's service, which wakes when the computer starts.
- **Database:** new tables `dormir`, `dormir_avisos` and `dormir_periodos` (only added).
- **En seco:** a branch that changes the app (a dependency update) in an app with `previews:` now runs its checks with `dryRun: true` against a copy of the branch: its pull request's copy, once that copy runs the branch's commit (up to the rollout timeout, 10 minutes by default), or, with no pull request yet, a short copy made only for the checks (`<app>-seco-<run>`, a quarter of the resources, a database of its own, never production's data), deleted when they end. A short copy counts toward `previews.max` but never makes a pull request's copy go: with no room, nothing runs and the run says why. A branch that touches neither the app nor its checks runs nothing en seco.
- **En seco:** `dryRunOn: published | preview | both` on a post-deploy task or on `tests:` says what it runs against; without it, the published release when only the checks changed and a copy of the branch when the app changed. It needs `dryRun: true`, and `preview` or `both` need `previews:`.
- **En seco:** a failure against the copy, or a copy that never comes to run the commit, only warns, as against the published release: **Passed, with a warning**, the GitHub check `action_required`, no merge by itself. When the branch's tests run en seco against its pull request's copy, the copy's own run of them waits for these, and the pull request's comment says how they went.
- **Run page:** the dashed *En seco* section says what the checks ran against: *the published release #N*, *the copy of pull request #N* or *a short copy of this branch*, with the copy's link while it lives; an app without previews gets a **Turn on previews** link to the book.
- **Database:** migration `0065_seco_con_copia.sql` adds the tables `run_dry_copies` and `run_dry_copy_tasks` (only adds).
- **Runs:** beside **Merge this branch**, a run's page offers **Just open the pull request** (the merge request on GitLab): it opens the branch's pull request with the same title and text, without anyone's yes and without merging it, and with it its preview copy where the app has `previews:`. One already open is linked instead. A collaborator or an administrator presses it; agents' keys cannot.
- **Apps:** an app's wall, the Universe, the Services page and the check before turning the wall on no longer wait for a cluster slow to answer (an update rolling out, a busy API server). The services catalog is given at once when it is older than 30 seconds while one new one is read behind it, never more than one at a time; a first one is waited for 2 seconds; a read gives up after 30 seconds; and one older than 10 minutes is not given. What the cluster has not said yet shows as grey placeholders, and the page asks again every few seconds.
- **CI:** the platform and API tests, like the store's, give each test a copy of one database migrated once per package (`internal/pgprueba`) instead of dropping the schema and running every migration again for each test, so `pruebas-api` and `pruebas-plataforma` take minutes less.
- **CI:** the store's tests copy one migrated database for each test (`CREATE DATABASE … TEMPLATE`) instead of dropping the schema and running every migration again, and `hack/ci-test.sh` connects to the throwaway Postgres with `synchronous_commit=off`. The store's tests had grown from about a minute (8 Nov) to six to eight minutes, the longest part of `platform:test`.
- **Environment:** the live settings no longer wait for the cluster. Which apps are outside the wall is now read on its own (the nodes, and the apps' pods only when a node does not enforce network policies), kept 30 seconds, and never the whole services catalog, which listed every pod, workload and service in the cluster on each look. When the cluster is slow to answer (during an update, for instance) the settings come at once and that one line shows a placeholder until the answer arrives, a few seconds later.
- **La Ruta:** every entry but lo vivido opens in two tabs, «The entry» and «Talk it over · N»: a conversation about the entry, kept with it, that anyone who sees the entry can join, every message signed (a person, the AI with its model, or an agent's key). Each person chooses who answers from the AIs the AI page offers now, with what a message costs (the platform's, your own key, the local model for free), or «My agent». The AI reads the entry, the related entries and the book's matching pages, says what it read, only talks, and keeps «The idea so far», which people may correct.
- **Encargos from a conversation:** «Done: make encargos» has the AI propose them, priced by the estimator; each is kept or left out, with its title, app (required), difficulty, who does it and what it comes after, and «+ Add another». «Make them» or «Make and send» (to the coding agent); «Save it as a decision in the Ruta» writes a decision entry linked to the one talked about. Each encargo carries the conversation, the idea and the decision.
- **AI page:** «Talking entries over» sets what one conversation may spend on paid models before it asks whether to go on (50 cents by default).
- **Agents (MCP):** `platicas_esperando` and `platica_responder`: a person's own agent answers the conversations that chose «My agent», signed with its key's name, in a cargo.
- **Database:** migration `0064_platicas` only adds tables (`platicas`, `platica_mensajes`) and a column with a default (`ai_settings.platica_cap_micros`); the previous version reads none of them.
- **La Ruta:** it opens on «For you» (*Para usted*): how many things wait for your word, the coding agent live, and one row with one action for each delivered encargo to review, entry tagged `por-decidir`, to-do tagged `para-usted` (or with your login), unconfirmed known failure to rate, comment nobody answered, and encargo nobody has (chosen right there, its app too). On a phone its four places (For you, Encargos, The agent, Journal) are a bar at the bottom; on a computer, tabs and a right column. Old `?tab=` links keep working.
- **Encargos:** cards with one main action, «Comment» and a «⋯» menu; a box that cannot be ticked says why (its app is missing, it is in the queue already, the coding agent is off), with the app chosen on the card; a bar at the bottom sends the chosen ones. Asking for one asks for its app (or «I do not know yet»). Dropping one asks on the page, with an optional reason.
- **The coding agent:** its queue (Ruta → The agent) shows what it does now (what it reads or tests, what it spent, «Stop»), what comes next in an order people set (drag, or the arrows), with when each was asked and the ones over 14 days marked old, what it finished and what it gave back. On the AI page, «Encargos at once» (1 by default, up to 3) lets it do several at once, never two of the same app.
- **Database:** migration `0063_cola_del_agente` only adds columns with defaults (`encargos.queue_pos`, `doing`, `stop_asked`; `ai_settings.code_concurrency`); the previous version ignores them and keeps doing one at a time.
- **One-computer installer:** it no longer asks for a GitHub login. It asks, when there is a terminal, where the code lives (GitHub, GitLab with its address, Bitbucket, or "I will choose on the setup page"; `--forja`/`--gitlab` or `RENDIMIENTO_FORJA`/`RENDIMIENTO_GITLAB` answer ahead), and ends by opening the setup page with the setup token in its address and that forja chosen; whoever authorizes it becomes the first administrator. Without a terminal (`curl … | sh` in a script) it no longer fails for want of a login. For GitLab and Bitbucket it prints the callback to set in the OAuth application (plain `http://localhost:8080`, which both accept).
- **Naming administrators ahead:** `RENDIMIENTO_ADMINS` (and its old name `RENDIMIENTO_GITHUB`, which keeps working) takes the names of Members, comma-separated: `ana`, `ana@gitlab.com`, `ana@git.example.com`, `ana@bitbucket.org`. The service has `ALLOWED_USERS` only when they were given.
- **Windows app:** the «Who signs in» step and its GitHub-username field are gone. After the download it starts rendimiento by itself, and «Open the setup page» takes the window to the setup page with the token in hand, where the person picks GitHub, GitLab or Bitbucket. The WSL distribution starts with nobody named.
- **Setup page:** a setup token in the address (`/?token=`) is sent at once, and `?forja=gitlab&gitlab=<address>` opens step 2 on that forja.
- **GitLab and Bitbucket on one computer:** an app from them is created without a webhook when rendimiento's address is `localhost` (gitlab.com refused to add one, so creating it failed), and every minute rendimiento asks its forja for new commits, as it already did GitHub.
- **Keys and settings:** the image registry, the DNS zone and target, the certificate issuer, the storage class, the ingress class and the public address change on the Environment page, each after its connection test (BuildKit pushes a test image and every node pulls it; the zone takes a test record; the issuer is ready; a test volume binds; the ingress controller runs; the address answers as this platform). «Change» is enabled only once the test passed for those values; nothing is saved when a step fails.
- **Keys and settings:** a changed setting is saved as a platform setting that wins over the ConfigMap's at start, and the platform's Deployments restart to use it (a minute or two). «Back to the ConfigMap's value» undoes it; `TESTED_SETTINGS=ignore` starts with the ConfigMap's values whatever was saved.
- **Volumes:** a volume that exists keeps its storage class when `STORAGE_CLASS` changes; new volumes take the new one.
- **Address:** `GET /api/identidad?n=…` answers a nonce signed with a key only the platform's processes have, so a new address can be proved to be this platform.
- **Keys and settings:** the log archive's S3 key and the Umami user change on the Environment page too, tested first like the other keys: the archive must accept the key, have its bucket and let it write, read back and delete a test object; Umami must let the user in and show it the websites. Nothing is saved when a step fails, and the platform uses the new one with no restart.
- **Keys and settings:** the off-site backups (R2) are listed as *Outside rendimiento*: an outside job copies them with its own secret, which the platform does not write.
- **RBAC:** the `rendimiento-llaves` Role also names `rendimiento-logs` and `rendimiento-umami`: run `make deploy` (or `helm upgrade`) once after updating.
- **Language:** a first visit picks Spanish or English by the first of the browser's languages that is one of them (in their order of preference); a browser that asks for neither (say, only Portuguese) starts in its country's, from Cloudflare's `CF-IPCountry` header: Spanish for Spanish-speaking countries, English for the rest. The language chosen with the switch still wins, and a request without `Accept-Language` (a crawler) is answered in English as before. The page gets only "es" or "en" (`<meta name="rendimiento-lang-pais">`); the country is never kept or logged. Without Cloudflare nothing changes.
- **Quickstart tests:** both quickstart tests (the one-computer installer and k3d) open the setup page before its return from GitHub, as a browser does, so they pass the state the return now checks.
- **Coding agent:** `merge_default_branch` and its merge commit now work on GitLab and Bitbucket apps too. On Bitbucket the commit has the branch and the default branch as parents; on GitLab, whose API writes one parent, rendimiento commits the resolution on the branch and on a passing branch `rendimiento/mezcla-…`, and merges the two through a merge request that closes by itself (a project that merges only by fast-forward or rebase, or always squashes, cannot take it).
- **Bitbucket:** a commit rendimiento writes (declared fixes, the coding agent) keeps an executable file executable, and its hash is the one Bitbucket says it wrote, not the branch's head after another push.
- **Environment:** the page is new: how it goes (a sun, with how many things are down and how many notices), what needs you (a card per problem, each with its action), the nodes as small houses with their processor and memory, and what the platform connects to (code, DNS, certificates, email, building, images, backups, AI). Capacity, every check, the version and the live settings are folded below.
- **Keys and settings:** a new page, `/environment/llaves`, for administrators: every key with its expiry and when it was changed, never its value. The Cloudflare token, the email (Resend) key and the platform's AI key change there: tested first against the service, saved only if every step passes (the Cloudflare token also in the ClusterIssuer's secret), and used with no restart, by every process within 15 seconds. Who changed which key and when goes to the database (table `llaves`) and the bitácora.
- **DNS:** the DNS check warns 30 days before the Cloudflare token expires.
- **Permissions:** new Roles let the platform update only its own `rendimiento-dns`, `rendimiento-notify` and `rendimiento-ia` secrets and, in `cert-manager`, the one secret the ClusterIssuer reads its Cloudflare token from (`cloudflare-api-token-secret`; patch the name in your overlay if yours differs, or set `certManagerSecret.name` with Helm). Run `make deploy` (or `helm upgrade`) once after updating.
- **Interface:** the pages that still waited on a blank space or a bare «Loading…» show the skeleton of what is coming, the same shape as the real thing: the Bitácora, the Log and the señales (a table's rows), Members (the list beside the detail), Use of the interface, Numbers, AI, the setup pages, New app (its repositories and the services to pick), the welcome page's board, an app's Notebook, Reliability, Visits and Caminos tabs, the Universe's latency and requests, a run's explanation and dry-run logs, the Mercado's preview and the mailbox's comment. Two new shapes join `components/esqueleto.tsx`: `EsqTabla` and `EsqBloques`.
- **Installation:** a new platform no longer needs GitHub. The setup page has three steps: the setup token (still the key, compared in constant time; it opens an install session in that browser, a cookie signed with the token), where the code lives (GitHub with its App's manifest, a GitLab or a Bitbucket workspace with their OAuth application, the same connections the Environment page makes), and who administers. Every door of the setup page answers 404 once the platform is installed.
- **First administrator:** whoever authorized the forja from the setup page comes back signed in as the first administrator, even if `ALLOWED_USERS` does not name them; on the third step they add the others by forja and username. The OAuth answer is bound to the install session.
- **ALLOWED_USERS and Helm:** both are optional now (`firstAdmins` no longer required by the chart), and take the same names as Members: `ana` (GitHub), `ana@gitlab.com`, `ana@bitbucket.org`. The platform starts without members when it has a setup token.
- **Members:** «Add someone» picks the forja (only those connected), the username and the role, and says the name they will come in as and with which button.
- **Disconnecting a forja:** before removing a GitLab or a Bitbucket workspace, the Environment page names who could no longer sign in; the last forja an administrator signs in with can never be removed (409, in the API too).
- **Without GitHub:** Environment's GitHub card says «Connect GitHub» (an administrator creates the App from there, no token), New app shows no GitHub notices, and the environment check counts a connected GitLab or Bitbucket as where the code lives.
- **GitHub App setup:** the manifest's state is checked when GitHub comes back, so only the browser that started can hand rendimiento an App.
- **Renovate:** apps on GitLab and Bitbucket with Dependency updates on are covered too: a pod per connection, with `platform` `gitlab` (and its API as `endpoint`) or `bitbucket`, and the connection's OAuth token, refreshed first when it would not last the run. Its merge requests (pull requests) are built and checked like any other, and get the app's declared fixes by themselves.
- **Declared fixes:** they run and commit on GitLab and Bitbucket branches, and **Add … fix to rendimiento.yaml** opens its branch there, with the link to open its merge request (pull request).
- **Coding agent:** it works on GitLab and Bitbucket apps too: its branch, its commits and the merge request (pull request) opened when the encargo is delivered go through the app's forja.
- **Diagnostician:** the files changed since the last good run are listed for GitLab (compare) and Bitbucket (diffstat) apps too.
- **Words:** preview comments and checks, and the work board's errors, say "merge request !7" and "GitLab" (or "Bitbucket") on those apps, in English and Spanish.
- **Bitbucket:** a push of several branches at once runs each of them, and a merged pull request is noted in the libreta with its whole commit (the webhook gives 12 characters).
- **GitLab and Bitbucket tokens:** refreshing a connection's token is held by a Postgres advisory lock, so two processes never refresh it at once; the second reads the new one.
- **Bienvenida:** the welcome page says it deploys repositories from GitHub, GitLab or Bitbucket, and shows «Sign in with GitHub» only when the GitHub App is set up (`/api/setup/status` says so in its new `github` field); with no forja connected it still offers GitHub, which leads to the first-run setup.
- **Bitbucket:** apps can live on Bitbucket Cloud too. Connect a workspace on **Environment → Where your code lives** with an OAuth consumer of the workspace (Account read, Repositories write, Pull requests write, Webhooks read and write; callback URL `<your address>/api/forjas/bitbucket/callback`); **New app** then lists its repositories in a Bitbucket tab, and rendimiento adds each repository's webhook (signed with HMAC-SHA256), clones with the OAuth token, writes a build status on every commit, and opens and merges pull requests (only while their head is the commit tested). Its two-hour tokens are refreshed and kept each time. See the book's «Connecting Bitbucket».
- **Sign-in:** the welcome page signs in with any connected Bitbucket workspace too; link your Bitbucket account from **Your accounts**, or an unlinked one comes in as `nickname@bitbucket.org` when it is a member.
- **Update:** migration 0061 only adds the table `bitbucket_connections`. Renovate, declared fixes and the coding agent skip Bitbucket apps for now; Bitbucket Data Center comes later.
- **GitLab:** apps can live on GitLab too, gitlab.com or your own. Connect one on **Environment → Where your code lives** with an OAuth application of yours (scopes `api` and `read_user`); **New app** then lists its projects in a GitLab tab, and rendimiento adds each project's webhook, clones with the OAuth token, writes a commit status on every commit and opens and merges merge requests («merge when pipeline succeeds» when GitLab's pipeline still runs). See the book's «Connecting GitLab».
- **Sign-in:** the welcome page signs in with any connected GitLab too. Link your GitLab account from **Your accounts** (the account's menu) to be one person in rendimiento; an unlinked account comes in as `username@host` when it is a member.
